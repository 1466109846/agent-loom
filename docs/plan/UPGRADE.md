## 2. U-1：快照依据、覆盖与结论

### 报告与发布

`loom-core` 生成同一份 `QueryReport`，CLI 的 `--json` 保留结构化证据，CLI/MCP 文本复用核心渲染。

| 项目 | 已实现行为 |
|---|---|
| 版本 | 报告 `contract=2`；结构 `REVISION=8`，两者独立 |
| 快照 | `snapshot` 含 `generation`、`revision`、完成时间、范围类型及输入摘要；`snapshot_at` 等既有字段保留 |
| 覆盖 | `coverage.known` 区分已记录与未知；受管、未覆盖、未确定引用、排除目录/文件、凭据路径拦截及引用总数分列 |
| 未覆盖原因 | 超过单文件上限、非 UTF-8、无法读取、语法不完整、生成物、单文件事实过多分别统计 |
| 查询范围 | 方向、深度、实际检查的文件/引用数；关系 64、符号 40、未确定引用 24、每处候选 4 的检索截断另报 |
| 现场核对 | `verification.files/inputs/skipped` 交代一致、已变化、消失、未知或不可核对，不以局部一致宣布全项目新鲜 |

索引先取得 SQLite 写锁，再扫描并在同一事务内发布结构、代次、输入和覆盖；失败不发布半次快照。即使解析修订没变、文件也没变，成功的显式索引仍有新代次。查询从同一数据库读取事务取得一个已完成代次，关闭该事务后才进行结构现场核对。

代次由 `structure_snapshot` 的插入/更新触发器维护。安装触发器后，同修订旧二进制写快照也会推进代次；它没有同时更新新增的发布记录时，新查询把覆盖明细标为未知，不套用上代明细。旧库尚无代次或覆盖记录时，同样保留未知并提示显式 `loom index`；读取不补表、不重建。解析修订不兼容时拒绝读取并提示使用匹配版本。

### 有界核对与输入基线

核对按目标、返回关系两端、问题来源和 Rust 声明链选取，最多 **32 个源码文件**；源码和普通配置单文件读取上限 **1 MiB**，忽略规则单文件上限 **256 KiB**。一类 Go/ECMA/Rust 配置的完整集合不超过 16 项时逐项核对；超过后只选相关祖先目录，并保留不可完整核对状态。**这些是文件数量与单文件边界，不代表整次查询的累计读取字节预算。** 核对成本优化见 [S-26](BACKLOG.md#s-结构索引)。

| 输入类 | 快照基线与现场核对 |
|---|---|
| `rules` | 范围类型、项目内各级 `.gitignore`、`.loom/ignore`、适用的 `info/exclude`，外层规则仅保存汇总摘要；核对目标祖先及适用基础规则 |
| `go` | `go.mod` 的内容指纹与相关祖先位置的存在性 |
| `ecma` | `tsconfig*.json`、`jsconfig*.json` 内容指纹，相关祖先默认配置的存在性 |
| `rust` | `Cargo.toml` 内容指纹，相关祖先清单的存在性；声明链文件纳入源码核对候选 |
| `python` | 由受管快照取得祖先 `__init__.py` 包标记的存在性基线；内容变化不等于包状态变化 |

现场核对复用扫描准入规则，只沿目标祖先检查。项目绑定、忽略规则、嵌套项目、链接/联接、文件类型和凭据路径均参与判断；不扫描兄弟目录，不打开边界外的源码。排除目录只计已遇到的目录边界，不扫描其内容推算文件数。

已变或消失会进入缺口；超额、不可安全读取或缺少旧基线继续显示不可核对/未知。核对不更新索引，不新增后台进程，也查不出尚未纳入快照的新文件。Git HEAD 相同不能替代这些检查。

### 三种结论与文本预算

| `conclusion.verdict` | 含义 |
|---|---|
| `found` | 快照查到关系；仍可同时有 `gaps`，不能据此声称关系已全部找齐 |
| `none_in_snapshot` | 在本次快照、指定方向和受管范围内未查到本地关系；不代表当前项目不存在 |
| `gap` | 没有关系且存在阻碍判断的缺口，例如未索引、目标不在范围内、未覆盖、未确定引用、查询截断或已知输入变化 |

出边查询依据实际查过的文件及其未确定引用判断；入边查询还检查全快照的未覆盖、未确定引用和覆盖明细。现场核对的未知/不可核对另列状态，不把它包装成当前源码的否定证明。

结构文本的 MCP 预算为 **1,500 UTF-8 字节**，CLI 为 **6,144 字节**。查询上限与文本展示省略分开报告；文本仅省略完整证据行，并计数关系、未确定引用和符号，提供 `--json` 或缩小范围的续查入口。字节不是词元，JSON 诊断和 MCP 封装也不在预览文本字节内。

## 3. U-2：固定评测与比较口径

### 已冻结的输入

套件位于 `E:/loom/eval`，只用 Python 标准库，不联网、不调用模型、不执行样本代码。`questions.json` 固定样本版本、文件摘要、范围输入、夹具和问题；`labels/*.tsv` 固定逐条依据；`thresholds.json` 固定门槛，`run.py` 和 `compare.py` 分别执行与比较。

| 样本 | 语言 | 标签数 |
|---|---|---:|
| `loom-rust`，固定 `cc2a954` 导出 | Rust | 40 |
| `vue-element-admin`，固定 `6858a9ad67483025f6a9432a926beb9327037be3` | JS/Vue | 40 |
| `oh-memos`，固定 `810627efafacb7845f4a3cb2031ae8b0bf00473d` | Python | 40 |

共 **120 条标签**、**38 个问题**：26 个结构、4 个记忆、6 个任务、2 个预算拒绝。`oh-memos` 在这里是离线源码样本，不是 Loom 的运行依赖。运行在独立副本里，跳过已有 `.loom`，核对版本、文件摘要和范围输入；不使用开发库或已安装的 Loom 来冒充候选版本。

### 质量与成本

- **Precision 是已报告关系的正确率**：按工具声称的 `exact`/`likely` 分开计算，只评价标签覆盖的来源、行号和目标。缺失关系计召回损失，不计 precision 错误；标签之外的错边没有被这项指标穷尽。
- **召回**要求正例的目标和使用方行号同时命中，逐语言与旧基线比较。按标签类别的命中比例另作逐条对照，不能把 Rust 的漏连比例当成已报告关系的误报率。
- 固定门槛是 reported exact precision ≥98%、likely ≥95%，原先正确的标签无丢失、无新增错误，逐语言召回不退步；无此类别的标签或报告记 N/A。
- 错报不存在要求 0；contract 2 的全部适用结构问题须通过。项目隔离、凭据、预算、并发代次由仓库对应测试把关，评测脚本不冒领为已完成的外部检查。
- 六个任务的 `context` 与**同一候选二进制**的现有多次查询比较：正确依据不丢失，并且请求数或最终交付字节严格减少。某题字节略增但请求减少，不等于成本门槛失败。
- 文本交付、JSON 诊断、MCP 握手/封装分开记；没有分词器实测就只报 UTF-8 字节。已有 20 条经验检索基线不由这 4 个新问题替代。

`baseline/rev8.json` 已替换为与当前 runner/definitions 一致的 **rev8-v2**，最终质量与同场资源比较 PASS（198 checks）；逐语言数据、任务对照和报告位置见 [eval](../../eval/README.md)。基线自比较不代替候选质量比较。固定问题为 **36 通过、2 项旧失败**：S26（Python from-package 落到包而非子模块）、M01（独立 `recall` 不按锚点路径检索）；contract 2 全部适用题通过，错报不存在由 5 降为 0。U-3 自己先查锚点，不等于独立 `recall` 已补上该能力。

### 正式资源口径

正式对照使用 `run.py --peer-loom ... --only resources --rounds 5`，在同一调度中逐轮轮换候选/旧版先后（AB/BA），每轮独立复制样本。分别记录全量、无改动、单文件修改、`explain`、`impact` 的中位数、范围、轮数和峰值工作集；复制和初始化不计入被测操作，查询计进程启动及 JSON 输出，不清系统文件缓存。

每个样本、每个版本另开一次 `serve`，完成固定 `overview/explain/impact/recall` 调用后空闲至少 **30 秒**，再记录工作集。单版本五轮试跑不能替代同场对照；耗时中位数增加超过 10% 时给出解释，不能只用文本缩短宣称资源改善。本轮正式对照和追加刷新诊断均已完成，原始数值、增幅说明与报告见第 6 节。

## 4. U-3：显式只读任务上下文

### 已交付接口

| 参数 | 实际规则 |
|---|---|
| `target` | 必填，项目内相对文件路径；不接受越界或凭据路径 |
| `mode` | 必填，`explain` 查依赖，`impact` 查使用方 |
| `question` | 可选，最多 512 UTF-8 字节的空格分隔经验关键词；不带空格的中文整句算一个词 |
| `depth` | 1..3，默认 1 |
| `budget` | 1..6144，默认 1500；按最终文本的 UTF-8 字节计 |
| 入口 | CLI `loom context <target> --mode explain\|impact`；MCP `context` 使用相同参数与核心实现；CLI 可加 `--json` |

`context` 由调用方主动请求，不自动选择目标、不更新索引、不保存 `question`、不启动模型，也不写入或确认知识。结构、有效约束、人工职责和经验基线来自同一数据库读视图；结构核对基线在视图内取得，现场有界核对在读事务外完成，不承诺整个文件系统在交付期间原子不变。

### 四区、相关经验和来源

1. **身份与约束**：保留项目标识、目标和模式；选择当前有效、已确认的红线与非目标，不把提议当作生效约束。每类检索最多 64 条，检索或预算遗漏均有提醒；安全且预算容许时展示完整项目根。
2. **结构**：携带快照代次与时间，确定关系、可能关系及未确定引用分开，保留使用方行号，复用 U-1 的结论和核对状态。
3. **职责与经验**：人工职责带当前/需复核/消失/不可核对状态；经验先取锚定本文件的有效记录，再用关键词补查并去重。锚定候选最多 5 条，关键词补充最多 5 条；省略 `question` 时默认按**带扩展名的文件名**补查，文件名不足 3 个字符则不补查。显式空关键词不变成最近记录查询。
4. **缺口与续查**：数据源失败、结构和人工知识需复核、检索窗口、预算省略分别可见；附 `explain`/`impact`、`note get`、适用的 `recall` 和记忆编号 `manage get` 入口。

经验来源明确写作“锚定本文件”“关键词命中”或“提到本文件名”，保留类型、编号、日期和漂移提示；文本命中不被说成文件锚定。关键词复用已有排序与近似项折叠，候选查询窗口为 50 条，窗口外数量未知时如实说明；不增加全库语义召回。某一来源失败时，仍返回其余可用分区并保留失败状态。

### 装配和预算

核心先预留身份、状态、缺口、约束遗漏提醒与续查所需空间，再装入完整的脱敏证据行。首条同样受限，放不下时整行省略，不剪掉否定词或适用条件。检索省略与预算省略分别统计，长标题保留可取回编号；必要内容也放不下时拒绝预算并报告本次最低需求。

CLI 与 MCP 的文本来自同一个 `ContextReport.text`，含换行、来源、状态和续查的最终字节数不超请求预算。CLI `--json` 另含四区、`bytes`、`omitted.budget/retrieval`、`gap_codes` 及完整结构报告，整个诊断 JSON 不受 `text` 的字节上限。关系、符号、引用和深度限制继续生效，扩大文本预算不扩大检索范围。

此入口不改变 `overview`、`refresh`、`resume` 和自动开场的计量/去重规则。当前没有词元计量器，字节限制不能写成词元实测。
